## Findings

### [High] Gemini exploding scene never cancels its animation loop on dispose

- **File:** [src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js](src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js):253
- **Problem:** `animate()` always re-schedules itself with `requestAnimationFrame(this.animate)` and does not store the frame id. `dispose()` disposes the renderer and OrbitControls but never cancels a frame, never sets `this.renderer = null`, and never disposes cubes, explosions, geometries, or materials.
- **Evidence:** The loop’s only stop condition is `if (!this.renderer) return`. After `dispose()`, `this.renderer` is still truthy, so a queued callback keeps calling `this.renderer.render(...)` on a disposed WebGL renderer. `initialize()` can also be called twice and stack a second permanent loop.
- **Impact:** Leaving or re-entering the feature leaks a live render/update loop (CPU + WebGL). Currently latent in production because menu 5 does not mount the scene, but it is the class’s public lifecycle.
- **Recommendation:** Store the rAF id, cancel it in `dispose()`, null `renderer` / set a disposed flag, dispose owned meshes/materials, and make `initialize()` idempotent.

### [High] Double `start()` leaves an uncancellable extra animation loop (both 2D simulations)

- **File:** [src/gpt5.3-codex/features/bouncing-squares/BouncingSquaresSimulation.js](src/gpt5.3-codex/features/bouncing-squares/BouncingSquaresSimulation.js):25; [src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js](src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js):44
- **Problem:** Neither `start()` nor `startAnimation()` no-ops when a loop is already running. Each call starts a new `requestAnimationFrame` chain and overwrites the stored id, so `stop()` / `stopAnimation()` can cancel only the latest chain.
- **Evidence:** Path `start(); start(); stop();` (or `startAnimation(); startAnimation(); stopAnimation();`) leaves the first chain running. Violates the lifecycle invariant that per-frame work has a single owner and stop cancels it.
- **Impact:** Duplicated simulation and full-grid redraw work every frame until the canvas leaves the document.
- **Recommendation:** Return immediately when an animation id is already set.

### [High] Gemini bouncing squares lose click-to-spawn after stop/start

- **File:** [src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js](src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js):21
- **Problem:** The click listener is registered in the constructor, removed in `stopAnimation()`, and never re-attached in `startAnimation()`.
- **Evidence:** Path `startAnimation(); stopAnimation(); startAnimation();` — animation resumes, but clicks no longer call `addSquare`. The GPT sibling registers in `start()` and removes in `stop()`, so restart works there.
- **Impact:** After a menu teardown/re-init cycle the feature looks alive but spawning is dead.
- **Recommendation:** Register the same bound handler in `startAnimation()`, or do not remove it in `stopAnimation()`.

### [Medium] `scaleCube` always scales from size 1, not the drawn size

- **File:** [src/gpt5.3-codex/features/CoordinateSystem.js](src/gpt5.3-codex/features/CoordinateSystem.js):101 (identical copy: [src/gemini3.1-pro/features/coordinate-system/CoordinateSystem.js](src/gemini3.1-pro/features/coordinate-system/CoordinateSystem.js):101)
- **Problem:** `drawCube(startX, startY, size)` stores `_cubeProps = { startX, startY, size: 1 }`, discarding `size`. `scaleCube(m)` then computes `newSize = 1 * m`. It also always calls `this.draw()`, restoring the grid even if the UI hid it.
- **Evidence:** `drawCube(10, 10, 3); scaleCube(2)` draws size 2, not 6. No in-folder test covers `scaleCube`. Menus currently bypass it by passing `cubeScale * multiplier` into `drawCube` directly, so the bug is latent in the UI but real on the public API.
- **Recommendation:** Persist the actual `size`, preserve hide-grid state, and add a unit test for non-default and repeated scales.

### [Medium] 2D Y-axis labels contradict the Y-up cube mapping

- **File:** [src/gpt5.3-codex/features/CoordinateSystem.js](src/gpt5.3-codex/features/CoordinateSystem.js):91; [src/gemini3.1-pro/features/coordinate-system/CoordinateSystem.js](src/gemini3.1-pro/features/coordinate-system/CoordinateSystem.js):91
- **Problem:** Cube drawing converts logical Y with `startYCanvas = origin.Y - startY * scale` (mathematical Y-up). Axis labels for the same pixels use `fillText(-j, …, origin.Y - j * scale)`, so the region above the origin is labeled negative.
- **Evidence:** With origin Y = 256 and scale 9.5, `drawCube(10, 10, 1)` places the square at canvas Y ≈ 161 (above the origin), while the label at that direction is `-j`. X labels match `origin.X + i * scale` and are consistent.
- **Impact:** Users see a “cube” in the first quadrant of the drawing API sitting on negative Y ticks. Coordinate orientation is not a single convention.
- **Recommendation:** Label the Y tick at `origin.Y - j * scale` with `j` (not `-j`), and add a test that a positive `startY` lands on a positive tick.

### [Medium] Gemini exploding spawn/bounce ignore cube extent; sphere scale compounds radius

- **File:** [src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js](src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js):170
- **Problem:** Cubes spawn with edge length in `[1, 5]` (bounding radius up to ≈ 4.33). Spawn only does `position.multiplyScalar(0.8)`. Bounce uses a fixed `sphereRadius - 1`. Separately, `createSphereBoundary(8)` builds a geometry of radius 8, while `updateSphereScale(s)` sets `mesh.scale` to `s`, so world radius becomes `8 * s` (slider 8 → radius 64).
- **Evidence:** Default sphere radius 8: a size-5 cube spawned on the surface is moved to radius 6.4, then extends to ≈ 10.73, already outside the sphere. Physics reads `geometry.parameters.radius * sphere.scale.x`, so the scale API and the initial geometry disagree about what “sphere scale” means.
- **Impact:** Large cubes clip through the boundary. If `bindControls()` is ever wired, the first slider movement jumps the sphere far from the initial size.
- **Recommendation:** Treat sphere radius as one world-space value. Clamp spawn by `radius - cubeHalfExtent`. Use the same half-extent for bounce. Recreate or uniformly scale the mesh from a unit sphere.

### [Medium] Grok exploding UI allows a cube that cannot fit in the sphere

- **File:** [src/grok4.5/features/cubes-exploding/renderCubesExplodingSection.js](src/grok4.5/features/cubes-exploding/renderCubesExplodingSection.js):51; [src/grok4.5/features/cubes-exploding/BabylonCubesExplodingController.js](src/grok4.5/features/cubes-exploding/BabylonCubesExplodingController.js):144
- **Problem:** Sphere scale may be 4 while cube edge length may be 5 (`halfExtent ≈ 4.33`). `clampPointInsideSphere` then clamps the center to 0.01, but the cube still sticks out. `setSphereScale` does not re-clamp existing cubes.
- **Evidence:** `cubeHalfExtent(5) ≈ 4.33 > 4`. The math module is otherwise correct (outward-only bounce, per-cube extent, descending index removal).
- **Impact:** A valid control combination makes containment impossible; cubes intersect the wireframe immediately.
- **Recommendation:** Cap max cube scale by current sphere radius (or min sphere by max cube), and re-clamp live cubes when the sphere shrinks.

### [Medium] Exploding motion is frame-rate dependent (Gemini and Grok)

- **File:** [src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js](src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js):200; [src/grok4.5/features/cubes-exploding/BabylonCubesExplodingController.js](src/grok4.5/features/cubes-exploding/BabylonCubesExplodingController.js):326
- **Problem:** Both add a fixed velocity/rotation once per rendered frame. Gemini explosions expire after `maxAge = 30` frames. Grok’s 3D cube controller already scales rotation by `engine.getDeltaTime() / 1000`; the exploding controller does not.
- **Evidence:** On 120 Hz, cubes move and Gemini bursts finish about twice as fast as on 60 Hz. Throttled tabs run slower.
- **Impact:** Physics and explosion lifetime depend on the display, not simulated time.
- **Recommendation:** Step with elapsed seconds; express velocity/rotation and explosion lifetime in per-second units. Test equal elapsed time across different frame intervals.

### [Medium] Gemini exploding GPU resources leak on cube removal and burst end

- **File:** [src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js](src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js):31
- **Problem:** `checkCollisions` does `scene.remove(cube)` without `geometry.dispose()` / `material.dispose()`. `Explosion.update()` removes 20 particle meshes but never disposes the shared geometry/material. `dispose()` of the scene does not walk cubes or explosions either.
- **Evidence:** Each cube owns a unique `BoxGeometry` + `MeshLambertMaterial`. Grok disposes cube material/mesh on removal and sets `disposeOnStop` on particle systems.
- **Impact:** GPU memory grows with every collision in a long session.
- **Recommendation:** Dispose geometry and material when removing cubes and when an explosion deactivates; mirror that in scene `dispose()`.

### [Medium] GPT/Gemini coordinate menus expose no teardown; Gemini exploding controls are dead

- **File:** [src/gpt5.3-codex/features/coordinate-system/renderCoordinateMenuPage.js](src/gpt5.3-codex/features/coordinate-system/renderCoordinateMenuPage.js):71; [src/gemini3.1-pro/features/coordinate-system/BasicCoordinateMenu.js](src/gemini3.1-pro/features/coordinate-system/BasicCoordinateMenu.js):28; [src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js](src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js):118
- **Problem:** Coordinate menus register `change` listeners and return `{ coordSystem, canvas }` or nothing — no `cleanup()`. Gemini listeners are anonymous, so they cannot be removed. `CubesExplodingScene.bindControls()` is never imported by a page (`menu5` is a stub). If called, `scaleVal.innerText = val` throws when `#sphere-scale-val` is missing, and those listeners are also anonymous.
- **Evidence:** Grok pages return `cleanup()` that removes the exact registered handlers and calls `controller.dispose()`. Import search: only the Gemini exploding test file references `CubesExplodingScene`.
- **Impact:** Re-rendering a menu leaks listeners. The Gemini exploding feature cannot be used end-to-end.
- **Recommendation:** Return removable handler references; query inside the container; wire the scene or delete the dead API; null-check optional DOM nodes.

### [Low] 2D wall bounce inverts velocity even when already moving inward

- **File:** [src/gpt5.3-codex/features/bouncing-squares/BouncingSquaresSimulation.js](src/gpt5.3-codex/features/bouncing-squares/BouncingSquaresSimulation.js):78; [src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js](src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js):82
- **Problem:** Out-of-bounds squares always negate `dx`/`dy`. A click near the edge can spawn a square that is already overlapping the wall while moving inward, then get flung outward.
- **Evidence:** Grok exploding math only bounces when `dot3(position, velocity) > 0`. Gemini exploding does the same for the sphere. The 2D sims do not.

### [Low] Gemini bouncing squares have no spawn cap

- **File:** [src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js](src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js):32
- **Problem:** `addSquare` always pushes. Pairwise collision is O(n²) with no `MAX_SQUARES`.
