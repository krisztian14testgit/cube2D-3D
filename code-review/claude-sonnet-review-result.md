## 1. `src/gpt5.3-codex`

**Scope note:** this folder does not (yet) implement a `cube-3d` or
`cubes-exploding` feature — only `coordinate-system` (2D canvas grid/axes +
a pseudo-cube drawn with `CanvasRenderingContext2D`) and `bouncing-squares`.
The "Cubes Exploding" checklist is therefore not applicable.

### Findings

- **Not real private state.** `CoordinateSystem.js` uses the
  `_underscorePrefix` convention (`_canvas`, `_origin`, `_cubeProps`,
  `_defaultProp`, `_numLinesX`/`_numLinesY`) instead of `#field`s, exactly the
  pattern the instructions call out to avoid
  (`src/gpt5.3-codex/features/CoordinateSystem.js:7,14,20,36`).
- **`console.error` as the only error path.** `scaleCube()` logs and silently
  no-ops instead of throwing or returning a result the caller can branch on
  when the multiplier is invalid or no cube has been drawn yet
  (`CoordinateSystem.js:140`).
- **Non-injectable randomness.** `randomDirection`/`randomBetween` in
  `BouncingSquaresSimulation.js` call `Math.random()` directly with no `rng`
  parameter (`features/bouncing-squares/BouncingSquaresSimulation.js:13-14`,
  used at `62-69`). The test file has to work around this with
  `vi.spyOn(Math, 'random').mockReturnValue(0)`
  (`BouncingSquaresSimulation.test.js:44`) instead of passing a deterministic
  function, which is exactly what the Determinism guideline warns against.
- **No pure math module.** Collision/bounce logic
  (`#resolveBoundaryCollision`, `#removeCollidingSquares`) is implemented
  directly inside `BouncingSquaresSimulation` rather than extracted into a
  small, dependency-free module analogous to `cubesExplodingMath.js`
  (`BouncingSquaresSimulation.js:73-111`).
- **Good compliance elsewhere:** real `#private` fields/handlers
  (`#handleCanvasClick`, `#animate`, etc.), `Object.freeze(DEFAULTS)`, guard
  clauses (`start()`/`stop()` early-return on missing canvas), and a
  `stop()` teardown that removes the click listener and cancels the
  animation frame (`BouncingSquaresSimulation.js:34-44`) — functionally
  satisfies the dispose/teardown rule even though it isn't literally named
  `dispose()`. `renderCoordinateMenuPage.js` destructures options with
  defaults and freezes `DEFAULT_CUBE_POSITION`
  (`coordinate-system/renderCoordinateMenuPage.js:3-4`), and `scaleCube()`
  does validate `multiplier > 0` before acting.
- **Testing:** tests are colocated, use descriptive `it` names, and name
  expected values as constants (`BouncingSquaresSimulation.test.js:4-13`).
  The `renderCoordinateMenuPage.test.js` suite exercises real DOM state, not
  just mocks.

## 2. `src/gemini3.1-pro`

**Scope note:** this folder implements `coordinate-system` (2D, shares the
same `CoordinateSystem.js` implementation as `gpt5.3-codex`),
`bouncing-squares`, and `cubes-exploding` (Three.js). There is no dedicated
`cube-3d` single-cube feature, so the 3D-cube-controller bullets of the
"Coordinate System & 3D Cube Rendering" checklist are judged against
`CubesExplodingScene.js` where applicable.

### Findings

- **Same `_underscore` issue, more widespread.** `CoordinateSystem.js`
  (`features/coordinate-system/CoordinateSystem.js:7,14,20,36`) and
  `BasicCoordinateMenu.js` (`_coordSystem`, `_canvasId`, `_hideCheckboxId`,
  `_sliderId`, `_cubeScale` at `BasicCoordinateMenu.js:4-8`) and
  `BouncingSquares.js` (`_squares`, `_coordSystem`, `_canvas`, ... at
  `bouncing-squares/BouncingSquares.js:4-8`) all use the underscore
  convention instead of `#field`s. `CubesExplodingScene.js` goes further and
  exposes **all** internal state as plain public properties
  (`this.cubes`, `this.renderer`, `this.scene`, ... at
  `cubes-exploding/CubesExplodingScene.js:47-59`) with no privacy at all.
- **Magic numbers inside a class body — the exact case the instructions
  warn about.** The `Explosion` class hardcodes `this.maxAge = 30; // frames`
  (`CubesExplodingScene.js:10`), a `BoxGeometry(0.5, 0.5, 0.5)` particle size
  (`:12`), and a `for (let i = 0; i < 20; i++)` particle count (`:15`); none
  are named module-scope constants. `CubesExplodingScene` also hardcodes
  `this.maxCubes = 10;` in the constructor (`:56`) instead of exporting a
  `DEFAULT_MAX_CUBES` constant the way `grok4.5`'s `cubesExplodingMath.js`
  does.
- **Non-injectable randomness.** `Math.random()` is called directly inside
  `Explosion`'s constructor (`:19-21`) and `spawnCube()` (`:171,184-193`)
  with no `rng` parameter, so this logic cannot be driven deterministically.
- **Physics inlined on live Three.js objects, not pure data.**
  `updateCubes()` and `checkCollisions()` operate directly on `THREE.Mesh`
  instances (`cube.position.length()`, `c1.position.distanceTo(c2.position)`,
  `c1.geometry.parameters.width` at `CubesExplodingScene.js:212,229,232-233`)
  instead of delegating to pure functions over plain `{x, y, z, halfExtent}`
  data, contrary to both the SRP chapter and the Cubes Exploding checklist.
- **GPU resource leak on collision removal.** `checkCollisions()` removes a
  colliding cube from the scene and the `cubes` array but never calls
  `cube.geometry.dispose()` / `cube.material.dispose()`
  (`CubesExplodingScene.js:242-250`), so long sessions leak GPU memory —
  directly contrary to the checklist bullet requiring geometry/material
  disposal on removal.
- **Correct behavior:** `maxCubes` input is clamped to `[10, 100]` in
  `bindControls()` (`:130-138`); `dispose()` does remove the `resize` and
  `mousedown` listeners and disposes the renderer/controls (`:282-293`).

## 3. `src/grok4.5`

### Findings

- **Real private fields throughout.** `BabylonCubeController` and
  `BabylonCubesExplodingController` both use `#field`s for internal state
  and bound handlers (`#resizeHandler`, `#pointerHandler`,
  `#contextMenuHandler`, `#nextCubeId` at
  `features/cubes-exploding/BabylonCubesExplodingController.js:25-29`).
- **Exemplary pure-logic module.** `cubesExplodingMath.js` is fully
  dependency-free (no DOM/engine imports), exports named constants
  (`MIN_CUBE_SCALE`/`MAX_CUBE_SCALE`, etc. — literally the pattern the
  instructions cite as the ideal), takes an injectable `rng = Math.random`
  in `randomCubeScale`/`randomVelocity`/`randomRotationSpeed`
  (`cubesExplodingMath.js:40,47,58`), and its `bounceVelocity()` explicitly
  normalizes `-0` to `0` (`:123-135`) — again, the exact function the
  instructions name as the reference example.
- **Consistent dispose/teardown.** Both controllers unregister every
  `window`/`canvas` listener and dispose engine, meshes, materials, and
  particle systems in `dispose()`
  (`BabylonCubesExplodingController.js:227-257`,
  `BabylonCubeController.js:150-157`).
- **One real gap:** `BabylonCubeController.setCubeScale(scale)` does **not**
  validate or clamp its input (`features/cube-3d/BabylonCubeController.js:127-133`),
  unlike the sibling `BabylonCubesExplodingController.setSphereScale()`,
  which correctly rejects non-finite/non-positive values
  (`BabylonCubesExplodingController.js:104-117`). This is a direct gap
  against the "Rotation/scale/color setters ... should validate or clamp
  their input" checklist bullet.
- **Cubes Exploding checklist fully honored:** `maxCubes` is clamped both at
  construction and via `setMaxCubes()` (`BabylonCubesExplodingController.js:40,119-122`);
  `collectCollisionIndexes()` operates on plain `{x, y, z, halfExtent}` data
  (`cubesExplodingMath.js:89-105`); collided cubes have their
  material/mesh disposed and are spliced from `cubes`
  (`BabylonCubesExplodingController.js:373-382`), and `particleSystems` are
  tracked and disposed on teardown (`:237-240`).
- **Testing:** `vi.hoisted` is used correctly to declare spies referenced
  inside `vi.mock('@babylonjs/core', ...)` factories
  (`features/cube-3d/BabylonCubeController.test.js:3-32`), `mockClear()` is
  used in `beforeEach` to reset hoisted spies while keeping their fake
  implementations, and `cubesExplodingMath.test.js` passes fixed
  deterministic `rng` functions instead of real `Math.random()`
  (`cubesExplodingMath.test.js:56-57`). One minor nit: the repeated
  boundary-value assertions in `cubesExplodingMath.test.js` (e.g.
  `clampMaxCubes(5)/(10)/(55)/(100)/(250)` at `:36-42`) use sequential
  `expect()` calls rather than `test.each`/`test.for`, which the guidelines
  prefer for this exact scenario.
