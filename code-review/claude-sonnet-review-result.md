### Findings

- **Not real private state (unchanged).** `CoordinateSystem.js` still uses
  the `_underscorePrefix` convention (`_canvas`, `_origin`, `_cubeProps`,

- **`console.error` as the only error path (unchanged).** `scaleCube()` still
  logs and silently no-ops on an invalid multiplier instead of throwing or

- **Non-injectable randomness in `bouncing-squares` (unchanged).**
  `randomDirection`/`randomBetween` call `Math.random()` directly with no
  `rng` parameter (`features/bouncing-squares/BouncingSquaresSimulation.js:13-14`),
  forcing the test to fall back on `vi.spyOn(Math, 'random')`
  (`BouncingSquaresSimulation.test.js:44`) instead of an injectable
  deterministic function.
- **Unvalidated cube scale.** `BabylonCubeController.setCubeScale(scale)`
  applies the raw input to `cube.scaling` with no clamping or validation

- **Good compliance elsewhere:** `CubesExplodingPhysics.js` is a genuinely

## 2. `src/gemini3.1-pro`

**Scope note:** this folder now has a dedicated `threejs-cube` feature
(`CubeState.js`, `CubeController.js`, `ThreejsCubeScene.js`,
`renderThreejsCubePage.js`) in addition to `coordinate-system`,
`bouncing-squares`, and `cubes-exploding`, closing the "no dedicated cube-3d
feature" gap from the previous report.

### Findings

- **Same `_underscore` issue in the older files (unchanged).**
  `CoordinateSystem.js`, `BasicCoordinateMenu.js`
  (`_coordSystem`, `_canvasId`, `_hideCheckboxId`, `_sliderId`, `_cubeScale`
  at `features/coordinate-system/BasicCoordinateMenu.js:4-8`), and
  `BouncingSquares.js` all still use the underscore convention. The new
  `threejs-cube` files go the other way and use **no privacy at all** —
  `CubeState`, `CubeController`, and `ThreejsCubeScene` expose every field as
  a plain public property (`features/threejs-cube/CubeState.js:2-6`,
  `ThreejsCubeScene.js:5-12`).
- **`ThreejsCubeScene` has no `dispose()`/teardown method at all.** `initialize()`
  registers a `pointerdown` listener on the canvas and a `resize` listener on
  `window` using anonymous inline arrow functions
  (`features/threejs-cube/ThreejsCubeScene.js:43-63`), so there is no stored
  reference to ever remove them, and `renderLoop()` schedules
  `requestAnimationFrame` recursively with no stored id and no way to cancel
  it (`:68-72`). This is a direct, unambiguous violation of the "any class
  that owns an engine/scene/renderer/`window` listener must expose a
  `dispose()`" rule, and it leaks a running render loop plus two global
  listeners every time the page is left and re-entered.
- **`CubeController.bindControls()` has the same gap.** Its six
  `addEventListener` calls on `scale-x/y/z`, `rot-x/y/z`, `rot-speed`, and
  `cube-color` are never paired with a `removeEventListener`/`dispose()`
  (`features/threejs-cube/CubeController.js:20-53`).
- **Stale render loop after `dispose()` in `cubes-exploding` (unchanged from
  prior report, still present).** `CubesExplodingScene.animate()` keeps
  calling `requestAnimationFrame(this.animate)` because it only guards on
  `if (!this.renderer) return`, but `dispose()` never nulls `this.renderer`
  or cancels the scheduled frame — it removes listeners and calls
  `renderer.dispose()`/`controls.dispose()` only
  (`features/cubes-exploding/CubesExplodingScene.js:253-256,282-294`). The
  render loop, and therefore `updateCubes()`/`checkCollisions()`, continues
  running against a disposed renderer/controls after teardown.
- **GPU resource leak on collision removal (unchanged from prior report).**
  `checkCollisions()` removes a colliding cube from the scene and the
  `cubes` array but never calls `cube.geometry.dispose()` /
  `cube.material.dispose()` (`CubesExplodingScene.js:242-250`), so long
  sessions still leak GPU memory; `Explosion.update()` has the same gap for
  its particle meshes when explosions expire (`:28-35`).
- **Magic numbers inside a class body (unchanged).** `Explosion` still
  hardcodes `this.maxAge = 30;` (`:10`), a `BoxGeometry(0.5, 0.5, 0.5)`
  particle size (`:12`), and a `for (let i = 0; i < 20; i++)` particle count
  (`:15`) as inline literals rather than named module-scope constants.
- **Non-injectable randomness (unchanged).** `Math.random()` is called
  directly inside `Explosion`'s constructor and `spawnCube()`
  (`CubesExplodingScene.js:19-21,171,184-193`) with no `rng` parameter.
- **`CubeState` does not clamp scale.** `setScale(x, y, z)` accepts any
  finite number, including negative or zero values, with no clamp
  (`features/threejs-cube/CubeState.js:9-13`), contrary to the "non-negative
  scale" checklist bullet — though it is otherwise a clean, dependency-free
  pure state object with sensible input guards for `NaN`/`undefined`.
- **Correct behavior:** `maxCubes` input is still clamped to `[10, 100]` in
  `bindControls()` (`CubesExplodingScene.js:129-138`); `CubeController`'s
  render-loop callback correctly delegates rotation to
  `sceneManager.applyRotation(state)` rather than inlining the rotation math
  itself (`CubeController.js:6-9`).

| Chapter | Score (1-10) | Justification |
|---|---|---|
| Modern JavaScript (ES2022+) Style | 3 | Every reviewed file uses `_underscore` fields or fully public state instead of `#field`s, and `CubesExplodingScene.js`/`Explosion` still hardcode a particle count, box size, and `maxAge` frame count as inline literals. |

### Findings

  `BabylonCubesExplodingController` both use `#field`s for bound handlers

- **Exemplary pure-logic module (unchanged).** `cubesExplodingMath.js`
  remains fully dependency-free, exports named constants
  (`MIN_CUBE_SCALE`/`MAX_CUBE_SCALE`, etc.), takes an injectable
  `rng = Math.random` in `randomCubeScale`/`randomVelocity`/`randomRotationSpeed`
  (`cubesExplodingMath.js:40,47,58`), and `bounceVelocity()` still explicitly
  normalizes `-0` to `0` (`:123-135`).
- **Consistent dispose/teardown.** Both controllers unregister every
  `window`/canvas listener and dispose engine, meshes, materials, and
  particle systems in `dispose()`
  (`BabylonCubesExplodingController.js:227-253`,
  `BabylonCubeController.js:150-157`); `BabylonCubeController.dispose()`
  additionally nils out `engine`/`scene`/`cube`/`cubeMaterial` references
  after disposal, which `gpt5.3-codex`'s otherwise-identical controller does
  not do.
- **One real gap persists.** `BabylonCubeController.setCubeScale(scale)`
  still does **not** validate or clamp its input
  (`features/cube-3d/BabylonCubeController.js:127-133`), unlike the sibling
  `BabylonCubesExplodingController.setSphereScale()`, which correctly rejects
  non-finite/non-positive values (`BabylonCubesExplodingController.js` via
  `clampCameraRotationSpeed`/`clampMaxCubes`). This is a direct, still-open
  gap against the "Rotation/scale/color setters ... should validate or clamp
  their input" checklist bullet.
- **Cubes Exploding checklist fully honored.** `maxCubes` is clamped both at
  construction and via `setMaxCubes()`
  (`BabylonCubesExplodingController.js` constructor and setter);
  `collectCollisionIndexes()` operates on plain `{x, y, z, halfExtent}` data
  (`cubesExplodingMath.js:89-105`); collided cubes have their
  material/mesh disposed and are spliced from `cubes`
  (`BabylonCubesExplodingController.js:379-380`), and `particleSystems` are
  tracked and disposed on teardown (`:237-240`).
- **Testing:** `vi.hoisted` is still used correctly to declare spies
  referenced inside `vi.mock('@babylonjs/core', ...)` factories
  (`features/cube-3d/BabylonCubeController.test.js`), and
  `cubesExplodingMath.test.js` passes fixed deterministic `rng` functions

  the repeated boundary-value assertions in `cubesExplodingMath.test.js`
  (`clampMaxCubes(5)/(10)/(55)/(100)/(250)` at `:36-42`) still use sequential
  `expect()` calls rather than `test.each`/`test.for`.
