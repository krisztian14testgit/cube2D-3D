### [High] Click-spawned cubes bypass the sphere clamp (gpt cubes-exploding)
- File: src/gpt5.3-codex/features/cubes-exploding/CubesExplodingScene.js:179
- Problem: `#handlePointerDown` forwards the picked surface point to `spawnCube`, which applies a fixed `position.clone().scaleInPlace(0.9)`. For large cubes (scale up to 5, `collisionRadius` up to ~4.33) 0.9 × boundaryRadius is not enough margin: at the default radius 15 a scale-5 cube is spawned at distance 13.5 with 13.5 + 4.33 > 15, i.e., already past the boundary. Because `shouldBounceFromBoundary` only bounces cubes moving outward (`position.dot(velocity) > 0`), a cube spawned out of bounds with an inward-pointing velocity never bounces; one moving outward just oscillates against the wall. There is also no clamping helper — the grok controller solves the same case with `clampPointInsideSphere(point, radius, halfExtent)` (src/grok4.5/features/cubes-exploding/cubesExplodingMath.js:140). Secondary: `clampMaxCubeCount` guards only `Number.isNaN` (CubesExplodingPhysics.js:13), so a non-numeric max-cubes input falls through `Math.min/max` and sets `maxCubes = NaN`, silently disabling all spawning (`cubes.length >= NaN` is always true) — grok's `clampMaxCubes` uses `Number.isFinite` (cubesExplodingMath.js:16).
- Evidence: violated invariant "spawning respects bounds" and "boundary handling accounts for cube extent". Concrete numbers above derive directly from `CubesExplodingPhysics.js` constants (MAX_CUBE_SCALE 5, `(sqrt(3)/2) * scale` collisionRadius in scene line 185).
- Impact: user-visible: big cubes spawned near the wall visibly stick out of the sphere or rattle at the boundary.
- Recommendation: clamp the spawn point with the per-cube `collisionRadius` (the same half-extent math the bounce check uses) instead of the fixed 0.9 factor.
