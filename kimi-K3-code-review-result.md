# Code Review Result — src/gpt5.3-codex, src/gemini3.1-pro, src/grok4.5

## Findings

### [High] Animation loop is never canceled on dispose (Three.js exploding scene)
- File: src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js:253
- Problem: `animate()` re-schedules itself unconditionally via `requestAnimationFrame(this.animate)` (line 256). No animation-frame id is stored and no running flag exists, so `dispose()` (lines 282-294) cannot stop the loop. After dispose, `this.renderer` is still truthy, so the `if (!this.renderer) return` guard never trips and the loop keeps calling `render()` on a disposed WebGL renderer forever.
- Evidence: violated lifecycle invariant "stop/dispose cancels animation". Concrete path: `initialize(); dispose();` → one rAF chain still alive; calling `initialize()` twice stacks a second permanent loop.
- Impact: leaked per-frame work and errors from a disposed WebGL context once the scene is wired into a menu (currently unreachable — see the `bindControls` finding — but it is the feature's public lifecycle).
- Recommendation: store the rAF id, cancel it in `dispose()`, set `this.renderer = null` (or a `#disposed` flag) so the loop self-terminates, and guard `initialize()` against double invocation.

### [High] Double `start()` spawns un-cancelable duplicate animation loops (both 2D simulations)
- File: src/gpt5.3-codex/features/bouncing-squares/BouncingSquaresSimulation.js:25; src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js:44
- Problem: Neither `start()` nor `startAnimation()` guards against being called while already running. Each call starts a new rAF chain; `animationFrameId` / `_animationFrameId` is overwritten, so `stop()` cancels only the most recent chain.
- Evidence: concrete path `start(); start(); stop();` → the first chain keeps animating. Violated invariant: "per-frame updates do not create unbounded work or duplicate callbacks".
- Impact: duplicated simulation/draw work per frame; the orphaned loop only stops when the canvas leaves the DOM.
- Recommendation: no-op `start()` when a loop is active (e.g., `if (this.animationFrameId !== null) return;`).

### [High] Restart leaves click spawning disabled (gemini bouncing squares)
- File: src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js:21
- Problem: The click listener is registered once in the constructor but removed in `stopAnimation()` (line 64) and never re-added by `startAnimation()`. Register/unregister references are asymmetric across the lifecycle.
- Evidence: concrete path `startAnimation(); stopAnimation(); startAnimation();` → animation runs but canvas clicks no longer add squares. The sibling gpt implementation registers in `start()` and removes in `stop()` symmetrically, so restart works there.
- Impact: user-visible: feature is half-dead after a stop/start cycle; also makes `stopAnimation()` a surprising "remove constructor wiring" operation.
- Recommendation: move `addEventListener('click', this._handleClickBound)` into `startAnimation()` (or stop removing it in `stopAnimation()`).

### [Medium] `scaleCube` always scales from size 1 instead of the drawn size
- File: src/gpt5.3-codex/features/CoordinateSystem.js:101 (identical copy: src/gemini3.1-pro/features/coordinate-system/CoordinateSystem.js:101)
- Problem: `drawCube(startX, startY, size)` stores `this._cubeProps = { startX, startY, size: 1 }`, hardcoding `size: 1` and discarding the `size` argument. `scaleCube(m)` then computes `newSize = 1 * m`.
- Evidence: concrete path `drawCube(10, 10, 3); scaleCube(2);` → expected size 6, actual size 2. `scaleCube` also always redraws the full grid (`this.draw()`), losing the hide-grid state. Neither reviewed folder has any test for `scaleCube` (only the out-of-scope claude-sonnet copy tests it), and no in-folder caller exists.
- Impact: public method produces wrong geometry whenever the cube was drawn with size ≠ 1; latent today because menus call `drawCube` directly.
- Recommendation: store the actual `size`, and redraw through the same grid/no-grid path as the current UI state; add a direct unit test.

### [Medium] Boundary bounce ignores the "moving outward" invariant (both 2D simulations)
- File: src/gpt5.3-codex/features/bouncing-squares/BouncingSquaresSimulation.js:78; src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js:82
- Problem: Velocity is inverted whenever the square is out of bounds, even when it is already moving inward. Position clamping masks most cases, but a square that is out of bounds while moving inward (e.g., spawned by a click at the very edge) is flung outward and can rattle at the boundary.
- Evidence: violated invariant "reverses motion only when moving outward". The reviewed grok code implements it correctly via `shouldBounceOffSphere` checking `dot3(position, velocity) > 0` (src/grok4.5/features/cubes-exploding/cubesExplodingMath.js:114).
- Impact: occasional stuck/oscillating squares at edges; inconsistent physics between model solutions.
- Recommendation: only negate the velocity component when it points outward (`dx > 0` at the right edge, `dx < 0` at the left edge, etc.).

### [Medium] Sphere boundary check ignores cube extent (gemini exploding scene)
- File: src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js:213
- Problem: `if (distance > sphereRadius - 1)` uses a fixed margin of 1 while cubes spawn with edge lengths in [1, 5] (bounding radius up to ~4.33). Large cubes visibly punch through the sphere wall before bouncing.
- Evidence: violated invariant "boundary handling accounts for cube extent". Grok's controller passes a per-cube `halfExtent = scale * sqrt(3) / 2` into the same check (BabylonCubesExplodingController.js:349).
- Impact: user-visible boundary violation for large cubes; collision/explosion behavior diverges from the sphere the user sees.
- Recommendation: compute the margin from each cube's bounding radius instead of the constant 1.

### [Medium] GPU resources leak on cube removal and explosion end (gemini exploding scene)
- File: src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js:242
- Problem: `checkCollisions` removes cubes with `scene.remove(cube)` but never calls `cube.geometry.dispose()` / `cube.material.dispose()` (each cube owns a unique `BoxGeometry`/`MeshLambertMaterial`). `Explosion.update()` (lines 31-35) removes its 20 particle meshes from the scene but never disposes their shared geometry/material either.
- Evidence: violated invariant "explosion/particle effects are created, updated, and disposed without leaks". The grok controller disposes cube material and mesh on removal (BabylonCubesExplodingController.js:379-380) and sets `disposeOnStop` on particle systems.
- Impact: GPU buffer/texture memory grows with every collision in a long-lived session.
- Recommendation: dispose geometry and material when removing cubes and when an explosion finishes.

### [Medium] No maximum-count limit in gemini bouncing squares
- File: src/gemini3.1-pro/features/bouncing-squares/BouncingSquares.js:32
- Problem: `addSquare` pushes without any cap. The O(n²) pairwise collision scan in `_handleCollisions` therefore grows unbounded with user clicks.
- Evidence: violated invariant "spawning respects configured limits" / "per-frame work is bounded". The gpt sibling caps at `maxSquares` (default 80) with `shift()`; the grok controller enforces `maxCubes`.
- Impact: frame-rate collapse after sustained clicking; unbounded memory.
- Recommendation: add a configurable `MAX_SQUARES` cap with a documented eviction policy.

### [Medium] Simulation advances per frame, not per unit time (both exploding scenes)
- File: src/gemini3.1-pro/features/cubes-exploding/CubesExplodingScene.js:200; src/grok4.5/features/cubes-exploding/BabylonCubesExplodingController.js:326
- Problem: Cube motion/rotation and `Explosion.maxAge = 30` frames (line 10) advance once per rendered frame with no delta-time scaling. On a 120 Hz display everything moves and expires twice as fast as on 60 Hz.
- Evidence: violated invariant "per-frame updates use stable time semantics". The sibling `BabylonCubeController` already demonstrates the correct pattern with `engine.getDeltaTime() / 1000` (BabylonCubeController.js:90).
- Impact: display-dependent simulation speed; explosion lifetime and bounce cadence differ across machines.
- Recommendation: scale velocity/rotation steps and explosion aging by frame delta time.

### [Medium] Menu pages expose no teardown; listeners are unremovable (gpt + gemini coordinate menus)
- File: src/gpt5.3-codex/features/coordinate-system/renderCoordinateMenuPage.js:71; src/gemini3.1-pro/features/coordinate-system/BasicCoordinateMenu.js:28
- Problem: `initializeCoordinateMenuInteractions` registers a `renderScene` closure on the checkbox/slider but returns only `{ coordSystem, canvas }` — no cleanup. `BasicCoordinateMenu` registers anonymous arrow listeners that can never be removed by reference. Both also resolve the canvas via global `document.getElementById` rather than container-scoped queries.
- Evidence: violated invariant "event handlers can be removed with the same references used to register them". The grok pages return a `cleanup()` that removes exactly the registered references (render3DCubePage.js:132-139).
- Impact: stale listeners if a menu is re-initialized in place; no owner-level disposal contract for these features.
- Recommendation: return a `cleanup` that removes the exact registered handler references; query the canvas within the passed container.

### [Medium] `bindControls` is dead, uncallable-in-production API (gemini exploding scene)

### [Low] Falsy `canvasElement` silently falls back to a global `#myCanvas` lookup
- File: src/gpt5.3-codex/features/CoordinateSystem.js:19 (same in the gemini copy)
- Problem: `if (params.canvasElement)` treats a falsy element as "not provided" and falls back to `document.getElementById('myCanvas')`, potentially binding an unrelated canvas instead of failing. Conversely, `BouncingSquaresSimulation.start/stop` guard `if (!this.canvas)` even though the constructor already throws when no canvas exists — dead guards masking the real failure mode.

- Impact: confusing failure behavior; error is attributed to the wrong element.
- Recommendation: distinguish "not provided" (`undefined`) from invalid values and throw for a missing element in one place (the constructor); drop the dead guards.
